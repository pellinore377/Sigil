### Fixed group and federation boundaries

- **G2.1 — Membership lifecycle:** authenticated invitation/context transfer and completion of joins, leaves, admin changes and device changes through the real service. Existing local policy accepts member-authorized changes, while the new service permits only administrators to submit opaque writes. This restriction is an implementation-introduced design issue. Resolve it without silently changing the original user behavior; an “admin relay” is a possible implementation, not a new product requirement or a predetermined solution.
- **G2.2 — Group-authorized delivery:** members must be able to communicate under authenticated group membership without requiring each member to be independently promoted to a globally verified direct contact. Existing distribution uses verified same-server pairwise sessions. A separate “group-scoped channel” architecture is not prescribed by the requirement.
- **G2.3 — Rotation/recovery:** integrate incoming/background authority synchronization and recovery when a member misses key distribution, including offline/reconnect and membership/device cutover. Existing outgoing epoch checks and explicit refresh are implemented; they do not complete this path.
- **G2.4 — Private membership:** reconcile the private authority with actual delivery metadata and test/document the resulting guarantees. Current mailbox packets expose Sender Key context and routing; anonymous authority proofs alone do not establish private membership for the combined service. This does not add the plan's deferred PIR/traffic-shaping research as a completion condition, nor promise invisible traffic relationships.
- **G2.5 — Earlier history:** authenticated authorization of recipient/source/range, encrypted retained-history transfer, pending/unavailable behavior, exclusions and fresh-device recovery. The existing `EarlierHistory(bool)` policy and ordinary recovery archives are foundations, not this transfer. Never export old live ratchets.
- **F3.1 — Native federation:** connect remote inventory/bindings/prekey claims to durable trusted sessions, sends, reception, acknowledgements and recovery. The ordinary event path still explicitly rejects differing homeservers; HTTP wrappers are not encrypted cross-server messaging.
- **F3.2 — Cross-server feature integration:** route group control/distribution and file access across homeservers, including issuer trust/credential handling and removal/retry cases. This is owned by #3, with #2/#7 dependencies; it is not counted as three independent implementations. Same-server #2 acceptance can be reported separately, but cannot be called complete federated groups.
- **F3.3 — Operational federation lifecycle:** peer retirement and retained-evidence capacity policy, with combined discovery/delivery/retry/quota/diagnostic acceptance. Existing diagnostics do not need to be rebuilt simply because older prose says they are missing.
