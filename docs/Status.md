## Browser maps and media

Browser location capture is permission-driven, bounded and foreground-only. Hiding/leaving the page stops capture and schedules existing live-share cleanup. Sending a current location or pin does not stop another live share. Browser maps render authenticated server vector tiles with a limited neutral Protomaps light/dark profile, local Newsreader/Sans labels, pan/zoom and an expanded viewer. They do not implement arbitrary MapLibre styles, address search or style downloads. Inline browser location cards show serialized map snapshots and open the interactive viewer. Snapshot rendering yields to interactive maps and releases its renderer after copying the image. One map renderer is active at a time. Avatar/radio indicators follow actual live-share freshness and expiry.

Map decoding rejects compressed/decompressed inputs over 2 MiB and preflights layer, feature, property and geometry budgets before decoding, including packed and unpacked protobuf integers. Cache/view limits remain bounded; style-specified network URLs are ignored. Resources use the authenticated own-server map broker.

Browser audio calling is present but has no successful live-call acceptance in this pass; it requires supported Opus WebCodecs and cross-origin isolation. Browser video/screen sharing remains unconnected. Android supports the existing encrypted audio/video/screen paths. The new RTC send path seals and reserves sequence numbers under the call lock, then transmits outside it. Per-media lanes preserve ordering; video I/O no longer blocks audio, receive or status processing. Audio thread/codec latency hints were added; jitter buffers and video bitrate were not blindly reduced/increased.

Received browser voice recordings discover missing WebM duration through a bounded local-blob seek without playback. Duration, playback, waveform seeking and reload were checked on an encrypted received recording. Waveform samples remain staging-only; received/reloaded recordings use a flat seek line. Persisted waveform metadata is not implemented.

Expanded media uses shared floating headers and real message reaction actions. Image/video captions remain in the timeline; image viewers use gestures and accessibility zoom actions without an extra toolbar. GIFs loop according to motion preferences without playback controls and show a small chip on timeline pictures. Video previews show a play overlay; photos have no type label. Browser viewers retain the mounted conversation and its theme beneath the dimmed/blurred overlay; Android blur depends on platform support and falls back to dimming.

## Speed and verification

Notes no longer wait before first load or reopen through the regular timeline. Superseded searches cancel, same-query results remain during refresh, and browser scans yield between bounded batches. Native search enumerates active group memberships without reconstructing every group timeline per batch. Android posts bypass the UI refresh mutex while preserving single-flight posting and stable retry IDs; the selected timeline updates after durable local enqueue. Healthy outgoing work wakes persisted messaging/file schedules immediately without clearing failure backoff or active reservations. Packet-submit recipient 404s retain queued bytes but do not stop unrelated outbound delivery; prekey/authentication failures remain blocking. Independent source review found no concrete regression in these paths; this is not race-stress evidence.

Image/GIF rows retain dimensions across lazy-list reentry. Browser decrypted image caching is bounded to 24 MiB/64 entries, requires fresh authorization on reuse, creates independently owned viewer URLs and rejects stale lifecycle insertions. Offscreen material views release rendering resources while keeping row geometry. Settled history uses exact rendered snapshots and releases GPU capacity; physical Android checks retain 25 unique objects with zero occupied GPU slots and unchanged pixels after reentry. Headed Chrome retains 40 dice/coins/cards after GPU release. A physical mixed-object timeline with real-time injected swipes measured 403 frames, median 11.97 ms, p95 19.39 ms and two frames above 32 ms; an identical empty-slot baseline measured p95 21.21 ms. This measured native object scrolling before snapshot retirement. Earlier batched virtual gestures distorted measurements and are not used as evidence.

Live Chrome testing against the deployed alpha.23-era Web build confirmed Web-to-Android photo, video, GIF, document, audio and dice delivery. One warm text send reached server acceptance in 555 ms and cleared the composer in 588 ms; these are one-sample observations, not recipient-delivery guarantees. Alpha.23 Android reproduced intermittent outbound sync errors; its test message eventually arrived. Alpha.24 is installed without clearing data and its test text arrived in Chrome. Reverse-direction media timing and deployed candidate-Web acceptance remain open. Chrome rendered the valid H264 fixture white both in Sigil and plain standalone HTML, while FFmpeg decoded colored frames; no app fix or browser-setting change is claimed for that independent rendering issue. Current client verification passes 404 tests with 10 ignored; Android and production browser builds pass. Browser uploads now receive explicit worker wakeups, and received media skips an unnecessary final one-second wait while preserving scheduler deadlines.

SQLite contention fixes cover group/history/invitation cursors, group credential-cache writes and expired/revoked history cleanup. The live warning was narrowed to sharing history; its cursor and cleanup regressions reproduced sqlite-5 before reserving the write transaction ahead of reads. Eleven history and nine invitation tests pass, including transfer/restart and authorization checks. Android diagnostics log only allowlisted sync stages and numeric SQLite codes. The warning did not recur during the brief post-install foreground check; longer user acceptance remains open. No keys, schemas or encrypted data were reset.

Posts now run a flush pass right after the local enqueue: it takes the messaging reservation, runs only own-device copies and the three send stages, and honors failure backoff, so a text reaches server acceptance without waiting for the next full pass or its eleven earlier stages. Foreground passes repeat prekey supply and session maintenance every 60 s instead of every second. The server adds `GET /client/v0/mailbox/wait?after=&timeout=` (1–25 s, 512 dedicated waiter slots, 35 s route deadline, exempt from the shared request slots); local and federated deliveries wake matching waiters, and an exhausted waiter pool answers immediately so clients fall back to polling. The browser holds the wait on the main thread with the worker's credential and the Android app holds it on an IO thread after closing the store; a hit forces the next sync due and re-arms at once, and only a run of instant returns backs off. The maintenance timestamp lives in the sealed schedule record (25-byte payload, 17-byte records still read) so Android's per-call store opens keep the 60 s throttle; wake passes skip the periodic contact poll. Ordinary deliveries validate in order and acknowledge concurrently. Flush passes now run beside a reserved pass, honoring failure backoff only and leaving the schedule untouched, because Android's one-second foreground pass otherwise held the reservation during most posts; send-intent and outbound cursors wrap within a pass instead of taking an empty one. Sessions whose recipient answers full (60 s) or unknown (300 s) wait in the new `outbound_backoff` table (native schema 78) instead of costing every pass; the live server showed one contact's Android mailbox at the 64-message per-sender cap, which produced continuous 507 responses. Flush results list each session's outcome for Android diagnostics. Measured on the phone after these changes: bubble at ~0.3 s, server acceptance and sent tick at ~1.2 s after the tap. Sync results carry per-stage millisecond timings and Android logs them under SigilTiming with command durations only. Phone measurements: an idle foreground pass costs about 270 ms native plus 60–70 ms of JNI/store-open overhead, of which the mailbox fetch is 70–100 ms and thirteen idle stages about 12 ms each; a post lands locally in about 350 ms and its flush accepts about 90 ms later. `synchronous=EXTRA` with DELETE journaling is the documented storage posture and was left unchanged. The one-second foreground poll remains as the fallback. Attachment steps now load up to four pending chunks, release the store transaction, transfer them concurrently (scoped threads natively, batched worker fetches in the browser), then record them; any success continues immediately and only a fully failed batch backs off. Downloads fill the first four missing chunks the same way. The transfer cursor now scans every cached file once per pass instead of sixteen, so idle files no longer cost an active upload a five-second pass. Server 5xx responses log status, method and path only. Live checks against the deployed build: Web text sends reached server acceptance 230–400 ms after the click (previous build 587 ms) and the phone's receipt returned within 2.2–2.4 s; a 3 MiB file uploaded its three chunks concurrently in 1.9 s and its message posted 300 ms after publish, with the phone showing it. One earlier run answered the attachment begin and publish with 503 and was not reproduced; the new log line is for the next occurrence. Server wait, schedule pass and batched transfer tests pass. The alpha.23 Web baseline was measured over an 83 ms hairpin path (7 ms direct to the LAN host).

Android foreground sync now wakes after outgoing changes and follows persisted deadlines. Browser sync no longer skips a pass because another UI operation owns the lock.
