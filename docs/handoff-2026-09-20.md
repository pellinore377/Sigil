## 4. Root causes found today (with evidence)

### 4.1 Sign-out revokes the device — THE BIG ONE
`Command::SignOut` called `revoke_device_online(session.device_id)`. Signing out therefore
**permanently revoked the device**, which is why:
- every peer saw "identity changed" for bedivere,
- the local store became unreadable to the next device,
- ~100 queued messages became undeliverable.

The deeper cause is that the stored `Profile` (`client/src/connection.rs:34`) has **no state for
"enrolled but signed out"**. `validate()` asserted
`profile.session.is_some() == profile.invitation.is_some()` — you hold either an unredeemed
invitation or a live session, nothing else. With nowhere to put a signed-out enrolled device,
revocation was the only option.

The fix (in the tree, unfinished): the **credential** is the device identity, not the session.
`sign_in_password_online` (`client/src/connection.rs:~638`) already resumes an existing device when
`enrollment_kind() != "new"` — it reuses `p.credential`, calls `network.session()`, and only falls
back to password auth on 401. So dropping just the session is sufficient and sign-in resumes the
same device. Also clear `rotation` and `oidc.link_secret`, which are only valid alongside a session.

Caveat I did not resolve: `prepare_oidc_enrollment` always mints a fresh credential, so the OIDC
sign-in path may still enrol a new device even with the profile intact. Check this — the user's
account appears to be OIDC (pocket-id runs on their infra).

### 4.2 Undeliverable message backlog — NOT A BUG, do not "fix" it
The phone's ~100 `send_errors` ("This operation expired or its message is no longer available" /
"Access denied") are messages queued to the revoked web device. **The system deliberately holds
them.** `client/src/peers.rs:~905-960` suspends devices that vanish from a peer's device set and,
once the user **accepts the identity change**, sets a `replacement` and calls `release_sessions`,
which reroutes the queued work to the new device. Deleting those intents destroys user messages.
I nearly did this. Don't.

The genuine defect here is presentation: a hundred send errors is the wrong way to say "one contact
needs re-verifying". The identity-change prompt is at
`shared/src/commonMain/kotlin/org/example/sigilprobe/ContactRequests.kt:29` ("Continue with new
identity"). User says they already accepted it and the banners persist — unexplained.

### 4.3 Web `account_access` probe can never succeed

The web refresh loop called it every 300 s; it fails, and the failure surfaced as

mismatch" and is not nailed down.

## 5. Calls — what is actually known (measured)

Committed and verified:
- **1080p30 phone→web works.** Phone captures 1920x1080@30 at 3.5 Mbit/s; browser decoded
  1920x1080 at 28–31 fps sustained over a minute. (c2d2909)
- Phone's 409 roster resend loop and the web's connect-retry spin are both bounded. (c2d2909)
- Abandoned calls close after 10 min instead of holding a slot for hours; per-account cap restored
  to 4, server max raised to 64; schema 38 adds `calls.started`. (a2548df)
- Per-frame SQLite write transaction removed from the media path — authority is now cached ~200 ms
  and invalidated by an authority revision so a peer block still cuts media on the next frame.
  (17d5ff6)
- Android playback is paced on the sender's cadence (`LEAD` 90 ms); the **local preview is not
  paced** (no journey, no jitter). Self preview is the encoded stream decoded back, like screen
  share — a second camera target made the camera crop the upright picture into a landscape buffer.
  (8473c12, d45fc65)

**The unsolved one: web→phone video.** The browser sends video as our own 1 KB SCP fragments over an
`RTCDataChannel`; the phone sends over a native RTP track. Same network, same moment:
- phone→server→web: 464 packets in, 464 out, decodes 24 fps — lossless.
- web→server: roughly half the fragments never arrive.

Channel reliability is **not** the lever — measured on live calls:
| setting | result |
|---|---|
| `maxPacketLifeTime: 120` | ~half lost, 8–14 fps of 20 arrive |
| `maxRetransmits: 0` | identical, 7–15 fps |
| `maxPacketLifeTime: 250` | encoder queue jams, output falls to 1 fps |
| `maxPacketLifeTime: 500` | channel carries **no** video at all, server counts zero |

Current committed setting is 120 ms with the web capped at 480x360@20 / 350 kbit/s.

### The native-track plan (task #7) and its real blocker
The SFU already reserves an RTP slot for browser camera: `Layout.uploads` is
`[audio, camera, screen]` (`calls/src/connect.rs:14`), and browser **audio** already rides RTP —
its transform seals a frame into exactly one SCP packet, which fits one RTP packet.

Video frames don't fit one packet, and a browser cannot hand raw RTP packets to a PeerConnection.
So with `RTCRtpScriptTransform` you hand Chrome a sealed blob and **Chrome packetizes it in the
negotiated codec's RTP format**, which the phone cannot reassemble — it expects our SCP header.

The SFU cannot bridge this for you: it runs str0m with `set_rtp_mode(true)`
(`calls/src/forwarder.rs:159`) and forwards packets without depacketizing.

Therefore the work is: **a codec RTP depacketizer on the native client**, plus the browser sender
transform, plus codec pinning. VP8 is the easiest payload format to reassemble from opaque
(encrypted) payloads — small descriptor, concatenate to the marker bit, no payload parsing. The
phone would then need `CODEC_VP8` added alongside `CODEC_VP9`/`CODEC_AV1` in
`app/src/main/java/org/sigil/compose/CallVideo.kt`.

Note `codec(kind)` in `calls/src/forwarder.rs:81` currently asserts AV1 for all video.

Do not try to reach 1080p30 web→phone by tuning bitrate/resolution/channel options. I spent most of
a night proving that road is closed.
